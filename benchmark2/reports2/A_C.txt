DEFECT 1
what: While an upload is running, clicking a file's "Remove" button does nothing at all — the file stays in the list and the user gets no feedback.
where: button.remove-button inside ul#file-list .file-item (click is delegated on #file-list; render() rebuilds the entire list on every requestAnimationFrame while uploading)
repro: Added 2 files, clicked Upload, then pressed and released Remove at the button centre with page.mouse.down/up. Hold times 20, 50, 80, 120, 200 ms -> item count stayed 2 of 2 in every trial, and no click event was dispatched on the button at all (a capture-phase document click listener recorded nothing for the press). The identical press while idle removed the item (2 -> 1) in all 6 control trials. Only a 0 ms same-frame down/up works. Cause: the per-frame full re-render replaces the <li> and its button between mousedown and mouseup, so Chrome never fires click on it. "Clear all", which sits outside the re-rendered list, still works mid-upload with the same 80 ms press.
severity: blocking
category: logic

DEFECT 2
what: Starting an upload rips keyboard focus off whatever control the user was on and dumps it on the document body, so the control can no longer be operated.
where: ul#file-list, rebuilt by render() on every animation frame while an upload is in progress
repro: Tabbed to a file's Remove button (document.activeElement = BUTTON.remove-button), started the upload, waited 120 ms -> document.activeElement = BODY. Reproduced 3/3 runs. Pressing Enter at that point removed nothing (item count 2 -> 2). Focus was still BODY after the upload finished.
severity: blocking
category: a11y

DEFECT 3
what: Activating "Upload" with the keyboard throws focus away — it lands on the body and is never restored when the upload completes.
where: button#upload-button (set disabled by render() for the duration of the upload)
repro: Focused #upload-button, pressed Enter. document.activeElement went BUTTON.upload-button -> BODY during the upload -> still BODY 2.3 s after it finished. Reproduced 2/2 runs. The user has to Tab from the top of the document again.
severity: minor
category: a11y

DEFECT 4
what: The second Tab stop is the visually hidden file input, so the focus indicator vanishes from the page entirely and a keyboard user cannot tell where focus is.
where: input#file-input (1x1 px, clip: rect(0px, 0px, 0px, 0px)) nested inside div#drop-zone[role="button"][tabindex="0"]
repro: Loaded the page and pressed Tab twice. Tab 1 = #drop-zone, clearly indicated (border colour measured rgb(159,172,204) -> rgb(78,110,232), background rgb(248,250,255) -> rgb(241,244,255) after the 160 ms transition settled). Tab 2 = #file-input, measured 1x1 px at (640, 397) with clip rect(0,0,0,0); a screenshot of the card taken at that moment shows no focus indicator anywhere on the page. Both stops do the same thing (open the file picker).
severity: minor
category: a11y
